## Цель эпика

Превратить распознанный протокол встречи в готовый к отправке/печати документ формата DOCX, который:
- 📄 Оформлен по стандарту Краюшкина (TNR 12, заголовки, таблицы «Сетка таблицы»)
- ⏱ Содержит таймкоды реплик (с гиперссылками на локальное видео)
- 👥 Реплики сгруппированы по ораторам
- 🖥 (опционально) Содержит встроенные скриншоты экрана демонстранта
- 🚀 Генерируется за короткое время (≤30 сек для протокола без скриншотов)

## Контекст эпика в бизнес-процессах

### As-Is (текущее состояние)

Алексей вручную:
1. Открывает Word/Google Docs.
2. Копирует текст из блокнота или прослушки.
3. Расставляет таймкоды вручную (часто с ошибками).
4. Сохраняет, отправляет участникам.
**Время:** 30–60 мин на 1-часовую встречу.
**Проблемы:** Пропускает реплики, путает ораторов, нет гиперссылок.

### To-Be (целевое состояние)

1. Алексей нажимает «Экспорт → DOCX» в HTML_MeetingProtokol.
2. Backend формирует DOCX по стандарту Краюшкина за ≤30 сек.
3. DOCX содержит всё: таймкоды, ораторов, скриншоты, гиперссылки.
4. Отправляет файл участникам.
**Время:** 30 сек + 1 мин на отправку.
**Выигрыш:** с 30–60 мин → 1.5 мин (в 20–40 раз быстрее).

## Acceptance Criteria эпика (сводные)

- ✅ AC-1: DOCX открывается в Word/LibreOffice без ошибок
- ✅ AC-2: Шрифт Times New Roman 12 пт, по ширине, без курсивов/жирного в основном тексте
- ✅ AC-3: Заголовки документа (18 пт жирный по центру), Heading 1 (16 пт), Heading 2 (14 пт), Heading 3 (12 пт)
- ✅ AC-4: Таблицы в стиле «Сетка таблицы» с повтором заголовков
- ✅ AC-5: Поля: слева 20 мм, справа/сверху/снизу 10 мм
- ✅ AC-6: Нумерация страниц внизу по центру
- ✅ AC-7: Таймкоды реплик рядом с текстом
- ✅ AC-8: Гиперссылка «▶ HH:MM:SS» рядом с каждой репликой (открывает локальное видео)
- ✅ AC-9 (если скриншоты включены): изображения встроены с привязкой к моменту
- ✅ AC-10: Реплики сгруппированы по ораторам (или сплошным списком — на выбор)
- ✅ AC-11: Язык проверки правописания — русский
- ✅ AC-12: Автор документа = «Алексей Краюшкин»

## Технические заметки

### Стек реализации
- **Backend:** Python + `python-docx` (>=1.1.0)
- **Шаблон оформления:** скрипт `scripts/render_vision_docx.py` (уже есть в проекте, адаптируется для протокола)
- **Гиперссылки:** `python-docx` через `add_hyperlink` (low-level OXML)
- **Скриншоты:** `add_picture` с `width=Cm(12)` (максимум по ширине страницы с учётом полей)
- **Размер файла:**
  - Без скриншотов: 100–500 КБ
  - Со скриншотами (10–30 шт): 5–50 МБ

### Потенциальные проблемы
1. **Длинные имена файлов с кириллицей** → при отправке через Telegram выдаёт «document too large» — копировать в короткое латинское имя (см. pitfall 7 в skill document-formatter-style-krayushkin).
2. **Размер DOCX >50 МБ со скриншотами** → предупреждать пользователя, опционально архивировать.
3. **Шрифт в Word vs LibreOffice** — TNR корректно отображается в обоих; но проверить на Astra Linux (там шрифт может быть не установлен).
4. **OXML для гиперссылок** — не все версии python-docx поддерживают «из коробки», нужна обёртка.

### Совместимость со стандартом Краюшкина

Использовать готовый шаблон `scripts/render_vision_docx.py` как основу. Дополнить:
- `add_table_caption_above` — для подписей таблиц «Участники встречи», «Решения»
- `add_hyperlink` — обёртка для гиперссылок на видео
- `add_picture` — обёртка для скриншотов с автоматическим подгоном размера

## Definition of Done

Эпик считается завершённым, когда:
1. ✅ US-015, US-016, US-017 реализованы и проходят все AC.
2. ✅ Сформированный DOCX проходит все 33 пункта чек-листа приёмки по стандарту Краюшкина.
3. ✅ Файл корректно открывается в Word 2019+, LibreOffice 7+, Google Docs.
4. ✅ XML-валидность всех файлов внутри DOCX-архива (проверка через `xml.etree.ElementTree.fromstring`).
5. ✅ Размер файла ≤10 МБ для протокола без скриншотов, ≤50 МБ со скриншотами.
6. ✅ Покрытие unit-тестами ≥70% для скрипта генерации.
7. ✅ Проверено на Astra Linux (шрифт TNR установлен, документ открывается в LibreOffice).
