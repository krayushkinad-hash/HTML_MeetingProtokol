## User Story
**Как** Алексей (P-01),
**я хочу**, чтобы пиковый RSS процесса backend при транскрипции 2-часовой записи не превышал 4 ГБ,
**чтобы** не получать OOM на рабочей станции (типично 16 ГБ RAM, из которых 8 занято системой).

## Контекст
- **Процесс:** Этап «Транскрипция» — техническое ограничение на ресурсы.
- **Боль персоны:** «OOM = вылет приложения = потеря результата работы».
- **KPI Vision:** 💾 Resources — «Пиковый RSS ≤4 GB».
- **Risk Vision:** #6 OOM — «Вероятность Высокая, Влияние Высокое».
- **Связь с Vision:** §9 Ограничения «Ресурсы / OOM» (7 конкретных лимитов).

## Acceptance Criteria

- **AC-1:** Given я загружаю 2-часовую запись, When идёт транскрипция Whisper Large-v3, Then пиковый RSS backend-процесса не превышает 4096 МБ (4 ГБ) на тестовом стенде.

- **AC-2:** Given мониторинг RSS работает, When процесс приближается к порогу 80% от лимита (3277 МБ), Then в UI появляется предупреждение «Приближаемся к лимиту памяти. Транскрипция замедлена».

- **AC-3:** Given порог превышен, When RSS >80%, Then процесс автоматически переключается на порционный режим (chunk = 10 сек вместо 30 сек), скорость транскрипции падает, но работа продолжается.

- **AC-4:** Given RSS превышает 95%, When критический порог, Then процесс ставится на паузу и в UI появляется «Память исчерпана. Транскрипция приостановлена. Закройте другие приложения и нажмите «Продолжить»».

- **AC-5:** Given у меня 2 разных процесса (транскрипция + чтение видео), When идёт обработка, Then каждый процесс ограничен своим лимитом (например, 3 ГБ + 0.5 ГБ).

## Технические заметки
- Мониторинг через `psutil.Process(os.getpid()).memory_info().rss`.
- Автопауза: `multiprocessing.Event` для graceful pause.
- Chunk = 30 сек (норма) → 10 сек (под нагрузкой).
- Whisper Large-v3 в режиме `fp16` (экономит память) + `beam_size=1` (экономит ещё).
- Для CPU-only режима — использовать `compute_type="int8"` (Vosk) или `quantized` Whisper.
